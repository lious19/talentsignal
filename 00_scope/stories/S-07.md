# S-07 — Opportunity Scoring System
**Agent:** ScoringAgent · **Fulfills:** REQ-003 · **Due:** Thu Jul 30
**Basecamp:** https://app.basecamp.com/3945211/buckets/24865175/todos/10116038295

## Story
As an agency manager, I want each opportunity scored consistently so the team prioritizes
objectively.

## Slice
`POST /api/opportunities/score` → `OpportunityScored` → opportunities with a normalized
0..1 score and factor breakdown

## Acceptance (Gherkin)
**Consistent bounded scoring**
- Given two identical opportunities
- When they are scored
- Then they receive the same 0..1 score and the same factor breakdown (idempotent)

**🛡 TRUST — Scores are auditable**
- Given any score
- When a manager inspects it
- Then the contributing factors and weights are visible, not a black box

## Build note (Ali's words)
> Add a ScoringAgent service that normalizes factors to 0..1, stores the breakdown, and
> feeds the prioritized queue in the React UI.

**Vibe-code it:** Determinism matters: same input, same score. That is what makes the
number trustworthy.

## The architecture question that must be answered first
There are now THREE things that "score": S-03/S-04's hidden-demand confidence (REQ-001),
S-06's candidate fit (REQ-002), and this opportunity score (REQ-003). **Are they the same
scorer or different?** Per the traceability matrix they are distinct requirements, so S-07
is its own ScoringAgent — but it must not silently duplicate the confidence heuristic.
Clarify: is the "opportunity score" the demand confidence re-exposed with a factor
breakdown, or a separate prioritization score combining demand + fit + other factors?
This is a design decision to settle before building, not during.

## Open questions / risks
1. Same-scorer-vs-different (above). Do not build a third parallel engine by accident.
2. **Weights are inspectable and versioned** — the trust scenario wants weights *visible*
   and *versioned*. That implies the config object gets a version stamp so a stored score
   can be traced to the weights that produced it. Design for that.
3. Idempotency is explicit here: identical input → identical score and breakdown.
