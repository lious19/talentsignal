## Story
As an agency manager, I want each opportunity scored consistently so the team prioritizes
objectively.

## Slice
`POST /api/opportunities/score` → `OpportunityScored` → opportunities with a normalized
0..1 score and factor breakdown

## Acceptance (Gherkin)
**Consistent bounded scoring**
- Given two identical opportunities
- When they are scored
- Then they receive the same 0..1 score and the same factor breakdown (idempotent)

**🛡 TRUST — Scores are auditable**
- Given any score
- When a manager inspects it
- Then the contributing factors and weights are visible, not a black box

## Build note (Ali's words)
> Add a ScoringAgent service that normalizes factors to 0..1, stores the breakdown, and
> feeds the prioritized queue in the React UI.

**Vibe-code it:** Determinism matters: same input, same score. That is what makes the
number trustworthy.

## Trust (TBI)
Scoring is idempotent and transparent; weights are inspectable and versioned.

## THE architecture decision — do NOT build a third scorer
Three things already "score": S-03/S-04 hidden-demand confidence (REQ-001,
`confidenceScore.ts`), S-06 candidate fit (REQ-002, `matchScore.ts`), and now S-07. An
opportunity ALREADY has a confidence_score from S-04. S-07 is NOT new scoring math — it:
1. **Reuses** the confidence heuristic (decision 007 weights, still PROPOSED).
2. Exposes a **structured factor breakdown** — each factor's *contribution and weight*,
   not just S-04's reason strings. e.g. `[{factor:"reposted", weight:0.32, value:1,
   contribution:0.32}, ...]`.
3. **Versions the weights** — the genuinely new piece. Stamp each stored score with a
   `weights_version`, so when decision 007's weights change, an old score still traces to
   the weights that produced it. This is what "weights are inspectable and versioned" means.
4. Guarantees **idempotence** — identical opportunity → identical score AND identical
   breakdown, tested.
5. Feeds a **prioritized queue** in React — opportunities ranked by score.

## Open questions / risks
1. **Don't duplicate the scorer.** If the plan introduces a new scoring formula rather than
   reusing confidenceScore/confidenceConfig, stop it. This is a consolidate-and-make-auditable
   story, not a new model.
2. **Weight versioning design** — where the version lives (a stamp in confidenceConfig, or a
   small versions table), and how a stored score references it. Log as a decision.
3. **Idempotence must be exact** — same input → byte-identical score and breakdown, like the
   S-06 idempotency test.
4. **Is the "opportunity score" the confidence score, or a blend of other factors?** The spec
   defines no other factors, so it's the confidence score re-exposed with a structured,
   versioned breakdown. If a plan tries to blend in fit or invented factors, flag it.
