## Story
As an agency stakeholder, I want repeatable evidence that the platform meets REQ-017's
latency and concurrency targets, so performance claims made in the demo are measured, not asserted.

## Slice
`load-test harness` → `LoadValidated` → per-endpoint p95/p99 at measured concurrency tiers,
honestly extrapolated toward the 1000-concurrent target where the tiers stop short of it.

## Acceptance (Gherkin)

- Given the Docker Compose stack running (db + backend on :4000)

  (analyze + opportunities), client-matchmaking, recommendation-engine, and
  hard-to-fill/targeting
- Then p95/p99 latency per endpoint per concurrency tier is captured and reported against
  REQ-017's <200ms normal / <500ms peak targets

**🛡 TRUST — honest measurement**
- Given a results/methodology doc produced by a real harness run
- When a reader re-runs the exact documented command against the exact documented environment
- Then they get numbers of the same shape as reported — never a fabricated or cherry-picked
  figure. (S-18 has no user-facing feature; its trust scenario is that its own measurement
  claim is reproducible.)

## The judgment calls (propose, log in decision 028, flag for Ali — no silent assumptions)
1. **1000-concurrent: demonstrated or estimated?** `scope.md`'s open question. Proposed: measured
   ramp on the real stack, honest extrapolation to 1000 — not a faked 1000-VU run, not an
   unevidenced estimate.
2. **Concurrency tier ladder** for the read/compute endpoints, and its per-tier duration.
3. **`/hidden-demand/analyze` is a bulk write, not a read** — it upserts the whole seed batch in
   one statement per call. It gets its own low ladder, interpreted separately: a
   `statement_timeout` hit there is the AC-4-2 cap firing by design, not a throughput failure.
4. **`pool.ts`'s default `max` (10, unset today)** — bump for a comparison run, or document as a
   found ceiling? Proposed: both — run once at today's default, once with an opt-in
   `DB_POOL_MAX` bump, to show the delta a one-line config change buys.
5. **Seed-data visibility for the read endpoints** — `/opportunities` already has an opt-in
   `?includeSeedData=true`; `/targeting` has none, and even with visibility fixed, the seed
   provider's generic titles can never clear the hard-to-fill threshold (0.4 max reachable vs.
   0.5 threshold) without title variation. Both gaps need fixing or the read/targeting numbers
   are meaningless.
6. **CI-guard scope** — an enforced threshold assertion now, or deferred to S-19 once CI exists?
   Proposed: deferred; S-18 ships a manual/opt-in harness only.
7. **Login's numbers are read against decision 006** (bcrypt cost-12 can alone exceed 200ms,
   proposed as an intentional documented REQ-017 exception, still unconfirmed by Ali) — not
   reported as a bare pass/fail against REQ-017.

## Watch-points (for plan review)
- Reuse, don't duplicate, the existing `*.latency.integration.test.ts` single-request diagnostics.
- Stays opt-in and structurally out of `npm test` / CI (same discipline as `RUN_TIMING_TESTS=1`,
  enforced here by living outside `src/` and `tests/` entirely, not by an env-var gate alone).
- `/auth/login` must never be hit per-VU — it's rate-limited to 10 requests/15min per IP. The
  harness authenticates once and shares the token; login's own load test is a small bounded
  request count, and its rate-limit ceiling is reported as a legitimate finding about its real
  sustained capacity, not a gap to defeat.
- `MARKET_SIGNAL_PROVIDER=seed` (plus `SEED_SIGNAL_COUNT`) must be set explicitly when running
  the harness, or `/hidden-demand/analyze` is measuring 2 hardcoded mock signals, not real volume.
- S-19's future CI workflow must not invoke `npm run load-test`, the same way it must not set
  `RUN_TIMING_TESTS=1`.

## Tests
Happy: a tier runs to completion and produces parseable p95/p99 for every scenario. Failure: a
tier where the server returns non-2xx or times out is captured and reported, not silently
dropped — and for `/analyze`, a `statement_timeout` is explicitly labeled as the AC-4-2 cap, not
an error to hide. Idempotency: re-running the harness against a freshly booted stack produces
numbers of the same *shape* (documented, not asserted bit-identical) — this is also the trust
scenario in practice.
