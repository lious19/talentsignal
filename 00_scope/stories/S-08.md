## Story
As a sales rep, I want to move a client through prospecting to closed on a live board so
nothing falls through the cracks.

## Slice
`POST /api/sales-pipeline/update` → `PipelineStageChanged` → a real-time pipeline board by
stage

## Acceptance (Gherkin)
**Live stage transitions**
- Given a client in prospecting
- When a rep advances the stage
- Then the React board reflects the new stage within a second (AC-4-5)

**🛡 TRUST — Every transition is audited**
- Given any stage change
- When it is saved
- Then an append-only audit row records who moved it, when, and from/to which stage

## THE foundation piece — the append-only audit trail
This is the S-05-equivalent for audit. Ali is explicit: "Wire the audit hook now so trust
work in R3 is a read, not a retrofit." This audit table is REQ-013, which S-15 formalizes.
Get it right now or retrofit painfully later.
- **Append-only must be enforced by DB constraint, not convention** (TBI rule 3: "the audit
  log is append-only by database constraint"). No UPDATE, no DELETE on audit rows — via
  revoked privileges or a trigger that blocks them. This is the key design decision.
- Each audit row records: **who** (the authenticated user from requireAuth), **when**,
  **from-stage**, **to-stage**.

## Other requirements
- **Sales_Pipeline table**, status enum: `prospecting | contacted | negotiation | closed`
  (Ch7). Tracks clients (FK to clients from S-05).
- **The notification hook** — "notifications fire but never leave the platform without a
  human." Internal-only for now; nothing outbound. Same negative-space discipline as S-04's
  no-outbound and S-06's no-auto-submit. The real outbound release gate is S-09.
- **React kanban board** — columns by stage, cards = clients.

## Open questions / risks
1. **Append-only enforcement mechanism** — revoked privileges vs. a rule/trigger. Decide and
   log; it's the foundation S-15 reads from.
2. **"Real-time... within a second"** — there are no websockets in this stack. This almost
   certainly means the board updates promptly after the action (optimistic update or
   re-fetch), NOT multi-user live push. Confirm that reading; don't over-build websockets.
3. **Are transitions constrained or freeform?** Can a rep jump prospecting → closed, or must
   it step through? Ali's note doesn't say. Judgment call — likely allow any change but audit
   it. Flag for Ali.
4. **Kanban interaction** — drag-and-drop is more complex; buttons ("advance stage") are
   simpler and satisfy the AC. Prefer the simpler unless there's reason not to.
5. **Notification hook** — internal only, proven by a no-outbound test. Evolves at S-09.
