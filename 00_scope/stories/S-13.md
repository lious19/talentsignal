## The key ideas
- **Simple time-series baseline, behind a service boundary** — heuristic-first. NOT real ML.
  A simple, transparent method (e.g. trend line / moving average) a stronger model can replace
  later without touching callers. Same discipline as every other scorer.
- **Confidence interval is the whole point** — the forecast returns a predicted value AND a
  band (upper/lower). "A forecast without error bars is a lie." The band comes honestly from how
  much the historical data actually varies (residuals), not a made-up number.
- **Outliers flagged, not smoothed** — unusual historical points are shown/flagged, never
  hidden. The trust scenario checks this explicitly.

## Design points / risks
1. **The forecast method** — a judgment call (trend line, moving average, simple exponential
   smoothing). Keep it simple and explainable. In a config object, marked PROPOSED, behind the
   ScoringAgent boundary. Don't reach for a heavy ML library.
2. **The interval width** — how the band is computed (e.g. prediction ± k × residual spread).
   Transparent and defensible. Log the method and any constant.
3. **Outlier threshold** — how far from trend counts as an outlier (e.g. > 2 std devs). A
   judgment call — propose, log.
4. **Historical data + seed** — "Given historical demand in PostgreSQL." Needs a monthly demand
   series with enough history to forecast. Reuse/extend the S-12 analytics seed. Same
   quarantine discipline; reconcile with S-19.
5. **Chart in React** — extend the hand-rolled SVG approach from S-12: a line for the forecast,
   a shaded band for the interval, and marked outlier points. Keep it simple.
6. **Latency 10s (AC-4-8)** — generous; measure, non-blocking like S-04/S-06/S-12.

## Tests
Happy path (forecast returns predictions + intervals from seeded history), the trust scenario
(interval present and outliers flagged, not smoothed), empty/short-history (graceful, not a
crash), latency non-blocking.
