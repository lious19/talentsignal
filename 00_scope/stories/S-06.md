## Story
As a sales rep, I want the best-fit candidates ranked for a specific job so I can respond
to a client fast.

## Slice
`POST /api/client-matchmaking/match` → `CandidatesRanked` → a ranked candidate list with
fit scores

## Acceptance (Gherkin)
**Ranked candidates with a fit score**
- Given a job description and the candidate pool
- When match runs in the Node service
- Then a ranked list with per-candidate fit scores returns within the 3s target (AC-4-3)

**🛡 TRUST — A human decides, the platform suggests**
- Given a ranked match list
- When it is shown
- Then it is labeled a suggestion with rationale; no candidate is auto-submitted to a client

## Build note (Ali's words)
> Implement a similarity score (skills/experience overlap) behind a MatchAgent service,
> expose ranked results, and render them with rationale in React.

**Vibe-code it:** Cosine-style overlap is enough for the demo. Show your work so recruiters
trust the ranking.

## Trust (TBI)
Matches are advisory with visible rationale; placement stays a human act.

## What Ali PRESCRIBED vs. what's a judgment call
- **Prescribed:** the method is cosine-style similarity on skills overlap. Ali named it —
  this is NOT an open scoring decision like the confidence weights were. Implement it.
- **Judgment call (small):** how skills-overlap combines with experience into one fit
  score, and whether `availability` is a score input or just a filter. Ali's build note
  says "skills/experience" and omits availability from the score — so availability is
  most likely a filter. Put whatever combination weight exists in a config object, marked
  PROPOSED, but recognize the core method is given, not invented.

## Depends on
S-05 — needs candidates (skills TEXT[]) and job_openings (requirements TEXT[]) to exist.
Both now built. Will need a few seeded candidates + a job to demo ranking.

## Open questions / risks
1. **The rationale must show WHICH skills matched**, not just a number — the "show your
   work" the trust scenario and Ali's note both demand. Same pattern as S-03's reasons array.
2. **No auto-submit.** There is no "submit to client" feature yet (that's S-09). The trust
   test is negative-space, like S-04's no-outbound: prove no auto-submission path exists.
   It should evolve when S-09 adds the human-release gate.
3. **Latency 3s (AC-4-3).** Measure it; keep any assertion non-blocking given the machine's
   memory limits, same as S-04.
4. **Idempotency:** same job + same candidate pool → identical ranking (deterministic).
