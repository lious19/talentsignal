## Story
As a sales rep, I want the platform to draft a tailored opportunity package that I review
and release so outreach is fast but always human-authorized.

## Slice
`POST /api/opportunity-package/draft` → `PackageDrafted` → a draft package pending human
release

## Acceptance (Gherkin)
**The platform drafts, it never sends**
- Given a scored opportunity
- When the PackageAgent drafts a package
- Then it is stored as a draft flagged AI-generated and is not delivered anywhere

**🛡 TRUST — Release requires an explicit human action**
- Given a drafted package
- When a human reviews and clicks release
- Then only then is it marked released, and the actor and timestamp are recorded

## Trust (TBI)
Nothing outbound leaves without an explicit human release; drafts are clearly labeled
machine-generated.

## Why this is the keystone
This is REQ-020 — "the AI drafts and suggests; a human reviews and releases anything that
would leave the platform" — the rule CLAUDE.md says overrides everything, now enforced in
code, not convention. Every "no-outbound" test since S-04 has been prefiguring this story.

## THE critical reading — the release flag IS the boundary
Ali is explicit: **"No delivery integration in the demo, the release flag is the boundary."**
So S-09 does NOT build actual sending (no email, no CRM write, no outbound anything). It
builds:
1. A **draft** state — AI composes a package, stores it flagged AI-generated, delivered
   nowhere.
2. A **release** action — an explicit human POST that flips the state to released and
   records who + when. This is the human-in-the-loop gate.
3. NO delivery. A future real sender would check "is this released?" before sending — but
   that sender is not in this story. If the plan reaches for email/CRM delivery, that's
   both scope creep and a violation of the story. Stop it.

Because delivery isn't built, the no-outbound tests still hold even for released packages —
nothing leaves the platform, ever, in the demo.

## Design points / risks
1. **The draft → released state machine.** Released once, terminal. Re-releasing an
   already-released package must be rejected/idempotent, and must NOT overwrite the original
   actor/timestamp. Only a draft can be released.
2. **"Flagged AI-generated"** — both a data flag AND a prominent UI label (TBI: "drafts are
   clearly labeled machine-generated"). Never let a released package lose that provenance.
3. **Release records actor + timestamp.** This is an audit event. Consider reusing S-08's
   append-only audit pattern so the release record can't be altered — the release is exactly
   the kind of accountability trail S-15 will care about. At minimum released_by / released_at.
4. **Composition is a heuristic/template**, not real LLM generation (heuristic-first rule).
   Compose from opportunity (company, score, factors) + matched candidates (S-06) + rationale.
   What goes in the package is a small judgment call — log it.
5. **The no-outbound trust test at its peak** — prove nothing leaves on draft AND on release.
   This is the story the whole "prove the AI can't send" discipline was built for.
6. **Judgment calls:** can a draft be edited before release? discarded? Minimum is
   review + release; editing/discard are nice-to-have — decide and log.
