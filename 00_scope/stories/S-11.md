## Story
As a recruiter, I want candidate recommendations with a reason and a way to give feedback
so the suggestions get better over time.

## Slice
`POST /api/recommendation-engine/recommend` → `CandidatesRecommended` → recommended
candidates with rationale and a feedback control

## Acceptance (Gherkin)
**Recommendations carry a why**
- Given a job requirement
- When recommendations return
- Then each candidate comes with a plain-English rationale within the 2s target (AC-4-9)

**🛡 TRUST — Feedback is captured for later learning**
- Given a recommendation
- When a recruiter marks it good or bad
- Then the feedback is stored against the recommendation for future tuning

## Build note (Ali's words)
> Extend MatchAgent with a recommendation route that returns rationale, persist thumbs
> feedback, and add the React feedback control.

**Vibe-code it:** Rationale plus feedback is the smallest honest learning loop. Bank the
signal now, tune later.

## Trust (TBI)
Every recommendation is explained; feedback is captured to check for and correct bias
over time.

## THE key reading — reuse S-06, don't build a parallel recommender
"Recommend candidates with a reason" is what S-06's matchmaking already does (ranked
candidates with rationale). So the ranking + rationale MUST reuse S-06's `scoreCandidate`
— same "don't build a parallel scorer" discipline as S-07 reusing the confidence scorer.
The genuinely NEW part of S-11 is the **feedback loop**: persist thumbs good/bad against a
recommendation, banked for later tuning. If the plan writes a new recommendation
algorithm, stop it.

## The feedback loop — bank now, tune later
Ali is explicit: "Bank the signal now, tune later." So S-11 STORES feedback but does NOT
retrain or act on it yet (heuristic-first). Nothing consumes the feedback — it's a banked
signal, honest scope-limit like S-09's release flag and S-10's confirm state.

## Design points / risks
1. **Reuse `scoreCandidate`** for the ranked recommendations + rationale (matchedSkills,
   reasons). Do NOT reinvent.
2. **Feedback storage** — a table keyed to the recommendation identity: which job, which
   candidate, thumbs good/bad, by whom, when. Recommendations are computed on the fly (no
   persisted recommendation row), so feedback is keyed by (jobId, candidateId) + recruiter.
   A judgment call — propose and log.
3. **Reversible feedback** — a recruiter can change good↔bad. One feedback per
   (recruiter, job, candidate), upserted, reversible (like S-10's confirm/dismiss, not
   terminal). Not an append-only audit trail — plain mutable state.
4. **Latency 2s (AC-4-9)** — measure it, non-blocking, same as S-04/S-06.
5. **The trust scenario** — feedback is stored against the recommendation. Prove with a
   test: mark good/bad → the feedback persists keyed to that recommendation.
6. **React feedback control** — thumbs up/down per recommended candidate, showing the
   rationale (never a bare number).

## Tests
Happy path (recommendations with rationale, reusing S-06), latency (non-blocking),
the feedback trust scenario (good/bad stored against the recommendation), idempotency
(re-marking is stable/reversible, one row per recruiter+recommendation).
