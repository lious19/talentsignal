## Story
As an agency manager, I want writes to client records deduped and reversible so
integrations never corrupt the CRM.

## Slice
`POST /api/crm/write` → `CrmWriteGuarded` → guarded, deduped, reversible CRM writes

## Acceptance (Gherkin)
**Duplicate writes are absorbed**
- Given the same client write twice
- When it is submitted
- Then the second is deduped and the end state matches one write (idempotent)

**🛡 TRUST — A bad update can be rolled back**
- Given an erroneous update
- When it is detected
- Then the guarded write can be reverted to the prior known-good state

## Build note (Ali's words)
> Add idempotency keys on CRM-bound writes, a dedupe check before persist, and a rollback
> path; write the twice-run test.

**Vibe-code it:** Idempotency is the whole game for integrations. Same input, same state,
every time.

## Trust (TBI)
CRM writes are idempotent and reversible, protecting client data integrity.

## The three pieces
1. **Idempotency keys** — each CRM-bound write carries a key. The server stores processed
   keys with their result; the same key submitted again returns the stored result WITHOUT
   re-applying. That's how "the second is deduped and the end state matches one write."
2. **Dedupe check before persist** — key-based (Ali says "idempotency keys"). Before writing,
   check whether this key was already processed.
3. **Rollback path** — a guarded write captures the **prior known-good state** (a before-image)
   at write time. A rollback reverts to it. This protects against a bad update.

## Context — no real external CRM
There is no real external CRM in this demo (providers are mocked). "CRM write" is a guarded
write to client records (the clients table from S-05). S-16 builds the *safe-write
machinery* — idempotency + dedupe + rollback — on that internal representation. This is the
mechanism REQ-020's human-release gate and S-08/S-15's audit trail exist to protect.

## Design points / risks
1. **The idempotency-key mechanism** — a table of processed keys (key → result/status). Repeat
   key → return stored result. Standard pattern. Reuse the DB-transaction discipline from
   S-08/S-09, don't reinvent.
2. **What counts as a "duplicate"** — key-based (Ali specified idempotency keys), NOT fuzzy
   content matching. Clean and defensible. Log the choice.
3. **What "rollback" restores** — the before-image captured at write time = prior known-good.
   How many levels (one undo? to a checkpoint?) is a judgment call — propose, log.
4. **Audit it** — record each guarded write AND each rollback, ideally to the append-only audit
   discipline from S-08/S-15, so writes/rollbacks are themselves recorded.
5. **The twice-run test** — Ali is explicit: "write the twice-run test." Same write twice →
   exactly one effect. This is acceptance scenario #1.

## Tests
The twice-run idempotency test (same write + key twice → one effect, second returns stored
result), the rollback trust scenario (bad update → revert to prior known-good state),
dedupe (repeat key absorbed), and failure paths.
