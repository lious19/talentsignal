# S-14 — Role-Based Access Control

**Basecamp:** https://app.basecamp.com/3945211/buckets/24865175/todos/10116038536

## Story
As an admin, I want admin, sales, and recruiter roles enforced everywhere so people only
see what they should.

## Slice
`guard(role)` on every route → `AccessChecked` → role-scoped views and 403s where appropriate

## Acceptance (Gherkin)
**Least privilege by default**
- Given a recruiter token
- When it calls an admin-only route
- Then the Express guard returns 403 and the attempt is logged

**🛡 TRUST — Ownership is checked, not just role**
- Given a sales user
- When they request another user resource
- Then access is denied unless they own it or are admin

## Build note (Ali's words)
> Add role + ownership middleware across the Express API, thread roles into React route
> guards, and cover the auth-denied path with tests.

**Vibe-code it:** Test the unauthorized path, not just the happy one. That is where real
security lives.

## Trust (TBI)
Every protected route checks session, role, and resource ownership; denials are audited.

## WHY THIS IS THE DANGER STORY
Every story so far ADDED something in its own corner. S-14 reaches into EVERY route already
built and enforces who can do what. Highest chance of breaking something that currently works.
When built, RE-RUN THE ENTIRE SUITE against a real database — the risk isn't the new code, it's
whether it quietly broke old code.

## The two hard design decisions (plan these before building)
1. **The permission matrix — who can do what.** Every route needs a role policy: admin (all),
   sales, recruiter. This must be DEFINED explicitly (a documented map), not guessed per route.
   It's a business decision — propose the matrix, log it, flag for Ali. Existing precedent:
   requireRole from S-05, PII gating from decision 009.
2. **How "ownership" is defined — the trickiest part.** The trust scenario denies a sales user
   another user's resource "unless they own it or are admin." But most resources (clients,
   candidates, opportunities) have NO owner column in the current schema. So either: (a) ownership
   applies only to resources that DO have an actor (e.g. recommendation feedback by recruiter_id,
   pipeline decisions by decided_by, released packages by released_by), or (b) add owner/created_by
   columns via migration. Decide the scope honestly — don't pretend ownership exists where the
   schema can't support it. Log the decision.

## Other requirements
- **403 + logged denial** — a denied request returns 403 AND is audited (structured log / audit
  trail), connecting to S-08's audit discipline.
- **React route guards** — thread roles into the front end so the UI also gates by role.
- **TEST THE UNAUTHORIZED PATH** — Ali is explicit and it's the trust scenario. Every protected
  route needs a test proving the wrong role gets a 403, and the ownership test proving a non-owner
  is denied. "That is where real security lives."

## Risks
1. **Regression across every existing test.** Enforcing roles will break tests that use the wrong
   token. Existing tests must be updated to authenticate with appropriately-roled tokens. Expect
   churn; re-run everything.
2. **The recruiter-account gap** — S-05 noted there's an admin-create-user route but confirm all
   three roles can actually be created to test against (admin, sales, recruiter).
3. **Don't lock yourself out of the demo** — make sure the bootstrap admin and a normal
   registration still work end to end after enforcement lands.
